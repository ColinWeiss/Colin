# TileChunkArrayPool 使用说明

## 池化是什么

池化就是"借了还, 还了再借", 而不是"用一次造一次, 用完就扔".

区块有两块大数组: `Infos`(物块信息, 每块约 0.7MB) 和 `Kernals`(物块行为引用, 每块约 0.15MB).
这个体量在 .NET 里超过 85000 字节就会直接进**大对象堆**(LOH). 大对象堆有个坏脾气:
分配快但回收贵, 而且回收不搬动对象, 反复分配释放会把堆搞出碎片, 逼着 GC 做 Gen2 压缩,
一次压缩就是十几毫秒的全场停顿. 游戏里每次跨区块都要装卸几个区块, 这个账单是持续滚的.

池化之后: 区块卸载时数组不扔, 还回池子; 下次创建区块直接租现成的, 分配归零, 碎片不再增长.

## 是什么来池化

`Colin.Core.Modulars.Tiles.TileChunkArrayPool`, 引擎侧静态组件. 责任边界如下:

| 角色 | 职责 |
|---|---|
| 池子本身 | 按数组长度分桶存取, 租借时清零 Kernals, 归还时限量(每种长度最多 64 组) |
| `TileChunk.DoInitialize` | 租借(区块创建的唯一入口, 游戏代码不用碰) |
| `TileChunk.ReleaseArrays` | 归还(只在异步存档真正落盘之后调用) |
| 游戏代码 | **什么都不用做**, 现有区块的创建和卸载路径已经全部自动接入 |

也就是说这是个透明基建: 你正常用 `Tile.CreateEmptyChunk` 和区块卸载, 池子就在背后工作了.

## 生命周期

```
CreateEmptyChunk
  └─ DoInitialize: RentInfos / RentKernals (Kernals 清零)
  └─ 区块活着: Infos/Kernals 正常读写
  └─ 被卸载: Chunks 移除, 排队异步存档
       └─ 后台存档线程读 Infos/Kernels 写盘 (数组还活着, 谁都不能还)
            └─ 落盘完成: ReleaseArrays 把字段置空, 数组入池
                 └─ 下一个区块 DoInitialize 时租走, Kernals 被清零, Infos 被 CreateInfo 整体覆写
```

## 两条安全命门(改代码前必读)

1. **归还时机是硬约束**: `ReleaseArrays` 的唯一合法入口是异步存档完成回调.
   存档线程在落盘前一直在读这两个数组, 提前还等于把正在读的内存转手给别人写.
   如果将来要新增归还入口, 必须先证明那一刻没有任何线程持有这块区块的引用.
2. **Kernals 租借时清零不可省**: 读档和放置只写有内容的格子, 空格子的行为引用永远是 null.
   不清零的话, 上一个区块的内核会残留成"看不见但能撞上"的幽灵物块, 这是池化最经典的翻车点.
   Infos 不需要清零, 因为 `CreateInfo` 对每个格子做整结构体赋值, 覆盖了全部字段.

归还之后 `Infos`/`Kernals` 字段被**故意置空**: 卸载后的区块再被误用会当场空引用炸出来,
好过拿着陈旧数组悄悄出错. 看到 NRE 指向已卸载区块, 先查是谁在区块死后还握着它.

## 怎么观察它是否在工作

池子挂了三个只读计数器, F4 调试页或临时日志里随时可以看:

- `TileChunkArrayPool.RentCount`: 累计租借次数
- `TileChunkArrayPool.ReturnCount`: 累计归还入池次数
- `TileChunkArrayPool.DiscardCount`: 超出容量上限被丢弃的次数

健康状态: 跑图一段时间后 RentCount 稳定增长而托管堆不再随装卸波动, DiscardCount 基本不动.
DiscardCount 涨得快说明同时装卸的区块数超过了 64, 可以调大 `MaxPerLength`(每组长约 0.85MB).

## 想给别的大数组也上池

池子按长度分桶, 天然支持任意长度. 新增一类大数组时:
写一对带语义的 `RentXxx / Return`(租借侧做该有的清零), 归还入口遵守同一条硬约束:
确认无人持有后再还. 不确定就先不还, 让 GC 兜底, 错过一次复用远好过还错一次.
